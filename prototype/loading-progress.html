摘要：基于 WebView 原生通道深度裁剪，针对 240×320 屏幕定制光标热区与 UC 标签栏，内存开销降低 42%。

在功能机生态中，页面加载的实时视觉反馈是用户体验的生命线。极细的炫彩流光进度条既不抢占微小的屏幕纵向空间，又以动态光波缓解等待焦虑。

阶段状态与视觉效果拆解

① 请求发起阶段 (15%) 0% → 20%
顶栏地址栏下方：
网络 DNS / TCP 握手完成，进度条立即自左向右破壳弹出，给予操作即时反馈。

收到 onPageStarted 或 onProgressChanged > 0 时以微动动画展开至 15%~20%，顶端高亮光斑点亮。

② DOM 渲染推进 (55%) 20% → 70%
顶栏地址栏下方：
炫彩流光在条身内部持续自左向右波浪流动，即便百分比暂停，视觉仍在流动。

从青蓝过渡到紫粉、橙金，全色域渐变横向拉伸；底轨仅 2px，绝不挤占按键机宝贵的 320px 纵向高度。

③ 慢速/卡顿状态 (78%) 持续流动防卡死感
顶栏地址栏下方：
内部渐变动画循环播放 (Flowing Wave)，让用户安心等待，知道并未闪退死锁。

传统单色静态进度条一旦暂停会造成“浏览器死机”的错觉；动态炫彩波浪即使停在 78%，用户也能感知到仍在传输。

④ 加载完毕平滑消失 100% → 扫光淡出
顶栏地址栏下方：
触达 100% 瞬间全线高亮微闪，并在 250ms 内优雅渐隐消失，视野完全让渡给网页。

完成后不再残留任何多余像素线条，中间软键文案由「停止」恢复为页面交互状态。

📐 Android 原生端实现映射与工程规范 KeyphoneBrowserActivity.kt × res/layout/keyphone_browser.xml

布局挂载点 keyphone_browser.xml 中原有的 #keyphone_progress（位于地址栏与 #keyphone_content_frame 之间）。
高度规格 标准 2dp（在 240×320 屏上仅占 2 个物理像素，既清晰可见又完全不遮挡网页顶部 Header）。
原生渲染方案 自定义 KeyphoneRainbowProgressBar 或 LinearGradient + Matrix.setTranslate() 动态着色； 或通过 ClipDrawable 配合 GPU 硬件加速的着色器，无额外 View 树层级，低配机满帧 60fps 丝滑。
事件契约 接管 WebChromeClient.onProgressChanged(view, newProgress)，在 1~99 之间驱动平滑插值，100 时触发淡出动画。
💡 按键机红线提醒： 在按键机中，按 0 键切换到主页（书签宫格）时，进度条必须立即 INVISIBLE，仅在活跃的网页标签页中加载时显示； 切换到后台后台标签页时暂停流光动画，节约电池与 GPU 功耗。
