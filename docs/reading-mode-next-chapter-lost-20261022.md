# 阅读模式「没有下一章」问题整理（2026-10-22）

> 只记录问题、证据与结论，不含代码改动。
> 相关实现文档：[`reading-mode-native-textview-plan.md`](./reading-mode-native-textview-plan.md) §12.7.4 / §12.7.5。

---

## 一、现象

1. 阅读模式读到一章末尾，**再也翻不出下一章**；界面上的感觉就是「这本书读完了 / 没有下一页了」。
2. 退出阅读模式后回到浏览器，同一章的页面上**明明有「下一章」**，点了还能正常继续读。
3. 期间阅读本身完全正常：翻页流畅、字号/背景可调、不卡不闪、没有空屏。

一句话：**正文没问题，只有「取下一章」这条路断了，而且断得没有任何提示。**

## 三、原因分析

问题由**三个独立缺陷**叠加放大，任何一个单独存在都不至于让用户以为「全书读完」。

### 缺陷 A（主因）：取章通道被渲染进程死亡带走后，**静默失败**

- 阅读模式的正文在原生视图里，但「取下一章」必须借助一个**隐藏的 WebView**（同源、带 Cookie，用同步 XHR 取章）。
- 渲染进程一死，这个 WebView 被销毁，`currentWebView()` 返回 `null`；代码在这里只是 `return false`。
- 用户侧表现：翻到章末没反应、没提示、没报错——**看起来就是「没有下一章」**。

### 缺陷 B（放大器）：WebView 重建**失败**，且失败后不再重试

- WebView 由对象池管理。渲染进程死亡后，旧 WebView 被 `destroy()`，但它的登记**仍留在池里**。
- 程序去池里取新实例时，池会顺手释放「旧的」；旧实例当初注册过「被释放时冻结/销毁自己」的回调，
  于是**刚建好的新实例被旧回调一起销毁**。
- 原来的恢复逻辑只在 6 秒后复查一次，发现没有 WebView 就**记一条 ERROR 收手**：
  该标签从此永久没有 WebView，直到用户退出重进阅读模式。

### 缺陷 C（另一个真实隐患，需一并处理）：JS 一次判定「结束」就终结整个会话

- 取章脚本只有在解析不到「下一章」链接时才回 `end`；宿主收到后立即把 `session.nextUrl` 置空。
- 链接解析会被站点页面变体（公告章）、反爬/半截 HTML、以及「next 已在已访问集合里就当结束」的兜底打偏。
- 一旦误判，本会话**再也不会尝试取章**，同样表现为「没有下一章」。本案不是它触发的，但它同样会让用户踩到。

## 四、关于「3 GB 内存为什么还会被杀」

用户的疑问是合理的：整机 2.5 GB 可用内存、应用才占 200 多 M，为什么会杀 WebView？

可以确定与不能确定的部分要分开看：

1. **渲染进程是独立进程，被杀不等于应用内存不够。** WebView 的网页渲染跑在
   `com.android.webview:sandboxed_process*` 里，它有自己的内存账本与优先级。系统或 Chromium
   本身都可能把它回收/重启，`didCrash=false` 正是「被外部杀掉」的语义（不是网页崩溃）。
2. **内存是否真的紧张，只能看当时的系统日志**，而那段日志已被冲掉。事后采集时机器空闲（1.1 GB 可用），
   不能反证当时不紧张——出事前后日志里有大量「主线程连续忙 1000~4000ms」「HardwareRenderer.nSyncAndDrawFrame」，
   说明当时 CPU/合成压力很大。
3. **已知的历史线索**：同一台设备此前就因为 `excessive cpu` 杀过渲染进程；说明它在系统眼里长期是资源大户。
4. 因此更准确的说法是：**「渲染进程被系统回收」是事实；「因为整机内存不足」是推测，尚未证实。**

### 关于「WebView 被杀之后能不能重启」

**能，而且本来就是这么设计的**——重建路径是：标签重新 `loadUrl` → 取一个新的 WebView → 重新挂上页面。

本案失败**不是「不能重启」，而是「重启逻辑自身有 bug」**（缺陷 B：新实例被旧实例的释放回调销毁）。
所以正确方向是修重建逻辑，而不是给 WebView 加更多保活。

## 五、本轮已做的处置（工作区改动，未提交）

| 位置 | 处置 | 作用 |
|---|---|---|
| `TabAdapter` 重载复查 | 复查发现没有 WebView 时，不再只记 ERROR，按上限（3 次）重新 `loadUrl` 触发重建 | 缓解缺陷 B（第二次通常能拿到干净实例） |
| `KeyphoneBrowserActivity.requestNextChapter` | 通道不可用时第一次就弹真实原因：「页面进程被系统回收，暂时取不到下一章；退出重进阅读模式可继续」，后续只记日志 | 消除缺陷 A 的「静默 + 误导」 |
| `KeyphoneReadingMode.js` `fetchNext()` | `end` 时附 `reason` / `current` | 让「真没有」和「没认出来」可区分 |
| `KeyphoneReadingMode.js` `chapterFrom()` | 只有 next 指向自己才算结束；重复章交给宿主去重 | 消除缺陷 C 的一条误判来源 |
| `KeyphoneBrowserActivity.handleChapterEnd` | 第一次收到 `end` 不采信：重建外壳按 SSR 重认一次，再回 `end` 才提示「已到最后一页」 | 消除缺陷 C 的「一次定生死」 |
| 取章回调日志 | 每次回调一行 `取章回调 ok/end/reason/url/next/会话next`（不含 html） | 下次可一眼定位 |

验证：真机 185→186 取章正常；`lintDebug`、`assembleDebug`、keyphone 单测全绿。
**渲染进程被杀场景本身未能端到端复现**（本机 shell 无权限杀 sandboxed 进程），因此缺陷 B 的根治仍待确认。

## 六、尚未根治，待决策

> **2026-10-23 更新**：已按 [`reading-mode-fetch-decouple-plan-20261022.md`](./reading-mode-fetch-decouple-plan-20261022.md)
> 的方案落地「取章解耦」——A（原生 HTTP，不碰 WebView）为主、B（专属取章 WebView）兜底，
> 实施记录见 [`reading-mode-fetch-decouple-impl-20261022.md`](./reading-mode-fetch-decouple-impl-20261022.md) §11。
> 下表保留作历史决策依据。

| 方案 | 内容 | 代价 / 风险 | 建议 |
|---|---|---|---|
| 1. 修对象池释放回调 | 释放时判断「这个实例还是不是自己的」，不是就不销毁；重建时彻底摘除旧实例 | 改动小，但涉及 WebView 生命周期，需仔细回归 | **优先做** |
| 2. 阅读时让 WebView 真正停摆 | 进阅读模式后停帧/停定时器，降低内存与 CPU 占用，从源头减少被杀 | 需实测同步取章是否仍可用 | 次优 |
| 3. 兜底取章通道（不依赖 WebView） | 直接用 HTTP + Cookie/UA 抓下一章 | 工作量最大，要处理 Cookie/UA/编码 | 最稳态方案 |

另建议：**阅读会话应能在「通道丢失」后自动恢复**（重建成功后自动续取），而不是要求用户退出重进。

## 七、排查方法沉淀

1. **先看应用落盘日志**：`/sdcard/Android/data/<包名>/files/log/YYYYMMDD.log`，
   debug 构建下是 DEBUG 级、逐行带时间戳，比 logcat 可靠。
2. **logcat 默认只有 256 KiB 环形缓冲**，Chromium 的帧日志两分钟就能把现场冲掉；
   需要现场时先 `adb logcat -G 16M` 放大（重启后恢复默认，注意放大动作本身会重置缓冲）。
3. 判断「是不是站点问题」最直接的办法：直接抓那几章 HTML，看「下一章」链接是否齐全，
   不要只凭应用内的提示下结论。
